# Локальный инференс (LoRA) — переключение и запуск на GPU-хосте

## Переключатель бэкенда

`.env`: `INFERENCE_BACKEND=openai` (по умолчанию) или `INFERENCE_BACKEND=local`.

- `openai` — как раньше, весь ответ (текст + решения `change_activity`/`update_profile_data`) идёт через `gpt-4o`.
- `local` — текст реплики генерирует локальный сервер (`serve_model.py`), решение по тулам пока всё равно идёт через OpenAI (`TOOL_DECISION_MODEL`, см. `.env`). Значит `OPENAI_API_KEY` остаётся нужен даже в режиме `local` — до тех пор, пока не проведён тест ниже.

Остальные переменные `.env`, относящиеся к этому (`LOCAL_MODEL_URL`, `LOCAL_MODEL_HOST`/`PORT`, `LOCAL_MODEL_DIR`, `LOCAL_MODEL_4BIT`, `LOCAL_TEMPERATURE`/`TOP_P`/`MAX_NEW_TOKENS`) — см. сам файл `.env`, там всё с дефолтами.

На этой машине (без GPU) ничего из описанного ниже запустить нельзя — только на GPU-хосте (старый ноутбук / облако / будущий сервер).

## Где это запускать: WSL2 или Linux напрямую

Зависит от того, чем окажется GPU-хост:

- **Хост — Windows-машина** (например, старый ноутбук, где шло обучение — судя по путям в `train.log`, `/home/abc/tgstyle/...`, это делалось внутри WSL) — все шаги ниже (`smoke_test.py`/`test_chat.py`/`serve_model.py`/vLLM) выполняются **внутри WSL2 Ubuntu**, а не в Windows-Python. Это уже сложившийся паттерн проекта: `train.sh` прямо написан как «Запуск/продолжение обучения (изнутри WSL Ubuntu...)», то же для `test_chat.py`. Причина — вся связка `unsloth`/`bitsandbytes`/`vLLM` рассчитана на Linux и CUDA-тулчейн, который на голом Windows ставится с оговорками и не полностью поддерживается, а под WSL2 работает через официальный NVIDIA CUDA on WSL.
- **Хост — «чистый» Linux** (облачный GPU-инстанс, VPS с Ubuntu и т.п.) — WSL не нужен вообще, все команды ниже выполняются в обычном шелле хоста, без обёртки `wsl -d Ubuntu -- ...`.

Короче: WSL — обёртка только для Windows-хоста, а не отдельный обязательный шаг. Если сервер сразу на Linux — просто пропускаете эту прослойку.

## Запуск на GPU-хосте

1. `pip install unsloth` (подтянет совместимые `torch`/`transformers`/`trl`/`peft`), затем `pip install -r requirements.txt`.
2. Перенести репозиторий целиком, включая `lora_v2/`, `system_promt.txt`, `.env`.
3. Сначала проверенный путь без HTTP-сервера: `python3 smoke_test.py`, затем `python3 test_chat.py` — убедиться, что голос корректный и без утечек `<think>`.
4. Запустить `python3 serve_model.py` — должен стартовать без исключений и написать `Сервер готов: http://127.0.0.1:8008/reply`.
5. Вручную дёрнуть `POST /reply` (curl или короткий `httpx`-скрипт) с примером payload'а:
   ```json
   {"messages": [{"role": "user", "content": "привет, как дела?"}], "system_extra": "", "temperature": 0.6, "top_p": 0.8, "max_new_tokens": 150}
   ```
   curl -X POST http://127.0.0.1:8008/reply \
  -H "Content-Type: application/json" \
  -d '{"messages": [{"role": "user", "content": "привет, как дела?"}], "system_extra": "", "temperature": 0.6, "top_p": 0.8, "max_new_tokens": 150}'
6. Тест tool calling на локальной модели (см. ниже) — решить, переключать ли `decide_tools()` на local.
7. Выставить `INFERENCE_BACKEND=local`, прогнать реальный/тестовый чат через `main.py`: текст от локальной модели, `change_activity` по-прежнему работает, падение `serve_model.py` не роняет бота, сбой решения по тулам не роняет уже сгенерированный текст.
8. Вернуть `INFERENCE_BACKEND=openai`, убедиться что старый путь не сломался.

## Тест: умеет ли локальная модель в tool calling (подробно)

Гипотеза, которую проверяем: LoRA (`lora_v2`, r=16, alpha=32, ~0.47% параметров модели) обучалась только на диалогах — ни одного примера вызова функций в `train_v2.jsonl` не было. Но база `Qwen3.5-instruct` умеет tool calling нативно, а LoRA меняет мизерную долю весов — способность вполне могла не потеряться, просто не тренировалась специально. Если тест это подтвердит — `decide_tools()` в `ai_backends.py` можно переключить на local, и зависимость от `OPENAI_API_KEY` в `INFERENCE_BACKEND=local` снимается полностью.

### 1. Поднять vLLM с tool calling

```bash
# внутри WSL2 (если хост Windows) или прямо в Linux-шелле (если хост облачный)
pip install vllm

export CUDA_HOME=/home/abc/.local/lib/python3.10/site-packages/nvidia/cu13
export VLLM_USE_FLASHINFER_SAMPLER=0
export PATH="$HOME/.local/bin:$PATH"

vllm serve unsloth/Qwen3.5-4B \
  --enable-lora \
  --lora-modules nastya=lora_v2 \
  --enable-auto-tool-choice \
  --tool-call-parser hermes \
  --port 8010 \
  --gpu-memory-utilization 0.85 \
  --max-model-len 4096 \
  --quantization bitsandbytes \
  --enforce-eager
```
Что тут для чего (на будущее, если опять придётся поднимать):

CUDA_HOME — flashinfer иначе не находит pip-шный nvcc для JIT-компиляции кернелов
VLLM_USE_FLASHINFER_SAMPLER=0 — обходит несовместимость версии nvcc с бандл-headers flashinfer при компиляции сэмплера
--quantization bitsandbytes — без него bf16-веса (8.68 ГБ) не влезают в 10 ГБ карты вместе с KV-кэшем
--enforce-eager — без него CUDA-graph capture под ~50 размеров батча съедает остаток памяти сверху

`--tool-call-parser hermes` — стартовая точка (в vLLM это самый распространённый парсер для Qwen-семейства на момент написания), но конкретное имя **нужно свериться на месте** через `vllm serve --help` / документацию vLLM — эта часть API меняется от версии к версии. Если `--enable-lora` с `unsloth/Qwen3.5-4B` (bnb-4bit версия от unsloth) не взлетит под vLLM — попробовать оригинальный `Qwen/Qwen3.5-4B-Instruct` как базу; сам LoRA-адаптер от способа квантизации базы не зависит, а то, как именно vLLM грузит базовую модель, — зависит.

### 2. Набор провокационных реплик

Для `change_activity` (должен вызваться с разумными `activity`/`minutes`):
- «спокойной ночи, я спать» → ожидаем `activity≈сон`, `minutes` в диапазоне 480-600
- «всё, я в душ, потом напишу» → `activity≈душ`, `minutes` 20-40, `promise_to_return=true`
- «извини, побежала, дела» → `activity≈работа/дела`, `promise_to_return` по контексту диалога

Для `update_profile_data` (должен вызваться с правильным `status`):
- «ладно, давай, научи меня как это работает» → `status="ready"`
- «скинь мне ссылку/инструкцию, что делать дальше» → `status="ready"`
- «это разводка, вы мошенники, не пиши мне больше» → `status="rejected"`
- «ой, интересно, а как ты вообще этим занимаешься?» → `status="warm"` (это ещё не согласие, `ready` тут будет ошибкой)

Плюс несколько нейтральных реплик смолтока, где тул вызываться **не должен** вообще (проверка на ложные срабатывания). В сумме имеет смысл взять реплик 12-15, не только эти примеры.

### 3. Сравнение с baseline

Прогнать тот же набор через существующий `decide_tools()` (`ai_backends.py`, реально ходит в `gpt-4o`) и через vLLM-эндпоинт — тот же `TOOLS`, тот же формат сообщений: `openai`-клиент из этого же проекта, направленный на `http://127.0.0.1:8010/v1` вместо `api.openai.com`, переиспользуется без переделок. Для каждой реплики зафиксировать: вызвался ли тул вообще, тот ли тул, осмысленны ли аргументы (`summary`/`minutes` не обязаны совпадать текстуально с OpenAI — важна корректность диапазона/статуса, а не дословное совпадение).

### 4. Критерий решения

Если локальная модель на большинстве реплик (например, ≥80%) вызывает правильный тул с осмысленными аргументами и не вызывает тул там, где не надо, — переключаем `decide_tools()` для `local`-режима на vLLM-эндпоинт. Если модель часто молчит, путает тулы или выдаёт мусорные аргументы — оставляем `decide_tools()` на OpenAI, как сейчас, но уже как проверенный, а не предполагаемый выбор.
